    Installation

    Install the dependencies and configuration package for your storage backend.

    Namespaces

    Choose a target namespace before deployment.

    • Apply Storage resources to the target namespace.
    • Apply namespaced ProviderConfig resources in each Storage namespace.
    • Create controller Secrets in the namespace named by the ProviderConfig's Secret reference. MinIO uses a separate minio namespace by default.
    • Provider Storage creates the consumer Secret in the same namespace as its Storage resource. The Secret name is the principal name.

    EnvironmentConfig and Composition resources are cluster-scoped.

    For the examples in these guides, create workspace:

    kubectl create namespace workspace

    Prerequisites

    You need:

    • a Kubernetes cluster;
    • kubectl access to the cluster;
    • Crossplane 2.4.3 or later in the v2 series installed in the cluster.

    From this checkout, install the pinned baseline with the supplied Helm values:

    helm repo add crossplane-stable https://charts.crossplane.io/stable
helm repo update
helm install crossplane crossplane-stable/crossplane \
  --version 2.4.3 \
  --namespace crossplane \
  --create-namespace \
  --values deploy/crossplane-values.yaml

    Each backend's ManagedResourceActivationPolicy lists the managed resource types it uses. Selective activation requires a provider with safe-start support; older providers activate all their types.

    Dependency baseline

    The shared versions and runtime settings follow the EOEPCA deployment manifests. The backend manifests pin these versions:

    Component Version Used by
    Crossplane 2.4.3 All backends
    provider-kubernetes 1.4.1 All backends
    function-python 0.6.0 All backends
    function-auto-ready 0.7.3 All backends
    function-environment-configs 0.9.2 All backends
    provider-minio 0.4.5 MinIO
    provider-aws-s3 2.7.2 AWS, CloudFerro
    provider-aws-iam, provider-family-aws 2.7.2 AWS
    provider-opentelekomcloud 1.0.0 OTC
    provider-ovh 2.23.1 OVHcloud
    provider-openstack 0.10.0 CloudFerro

    All Configuration packages require Crossplane 2.4.3 or later in the v2 series. For an upgrade, update Crossplane first, then the shared providers, runtimes, and functions. Check their health before updating the backend Configurations.

    AWS IAM, the AWS provider family, OTC, and OVHcloud retain their existing pins because the EOEPCA Crossplane setup does not declare them. EOEPCA also installs provider-keycloak 2.24.1, which Provider Storage does not use.

    The Helm values disable default resource activation and configure Crossplane and its RBAC manager to run as non-root users with read-only root filesystems. The MinIO, Kubernetes, and function runtimes use the default seccomp profile, drop Linux capabilities, and disable privilege escalation. The Kubernetes provider enables watches, polls every five minutes, limits reconciliation to 10 per second, sanitizes Secret data, and has a 1 GiB memory limit. Keep each Provider's and Function's runtimeConfigRef when applying these settings. Manage shared packages and runtime configs under one owner.

    The build and test workflows use Crossplane CLI 2.4.1. The CLI has a separate release cycle; renders and schema checks target Crossplane 2.4.3.

    1. Install backend dependencies

    For a cloud backend, install bootstrap-iam.sh and run configure, apply, and verify as described in Cloud IAM bootstrap. Choose where to run bootstrap: a specific host, a CI/CD pipeline, or a local machine. Compositions use a ProviderConfig to authenticate cloud API calls. For static credentials, its credentials.secretRef must point to a controller Secret. IAM apply creates the cloud identity and saves credentials locally. Run verify and check its result before you render and deploy the Secret. Then configure the ProviderConfig reference:

    export CROSSPLANE_OVH_NAMESPACE=workspace
bootstrap-iam.sh ovh render-secrets |
  kubectl --context storage-cluster apply --server-side -f -

    Replace ovh, its namespace variable, and storage-cluster for your backend and deployment. The Secret name, namespace, and key must match the ProviderConfig. See Deploy controller Secrets for all four backends. AWS workload identity uses external trust instead of a static controller Secret. CloudFerro needs a project ProviderConfig and EnvironmentConfig before Storage reconciliation.

    Follow the dependency guide for your backend to edit the manifests:

    Backend Dependency guide
    MinIO MinIO dependencies
    AWS AWS dependencies
    OTC OTC dependencies
    OVHcloud OVHcloud dependencies
    CloudFerro CloudFerro dependencies

    The dependency manifests use the same order for every backend:

    Manifest Scope Purpose
    00-mrap.yaml Cluster Activates the managed resource types used by the backend.
    01-deploymentRuntimeConfigs.yaml Cluster Configures provider and function deployments.
    02-providers.yaml Cluster Installs the providers.
    03-providerConfigs.yaml Cluster or namespace Configures provider authentication. Apply namespaced configs in every Storage namespace.
    04-environmentConfigs.yaml Cluster Defines endpoint, region, and backend settings.
    functions.yaml Cluster Installs the Composition functions.
    rbac.yaml Cluster Grants provider-kubernetes access and Crossplane access to native Secrets.

    Edit all placeholders before you apply a manifest. Apply the numbered files in order, then apply functions.yaml and rbac.yaml.

    Manage shared functions and provider-kubernetes once. Keep the ProviderConfig's cloud account or project consistent with the EnvironmentConfig.

    Environment settings

    function-environment-configs merges config data in this order:

    1. default.
    2. spec.crossplane.compositionRef.name.
    3. spec.environmentName, when set.
    4. The Storage's metadata.name.

    Later values override earlier values. Nested maps retain fields that later configs do not set. Missing configs are skipped. Local renders without compositionRef use the backend Composition name.

    The function selects configs from XR fields by matching labels. Set storages.pkg.internal/name to the config's own name and keep that label value unique. The EnvironmentConfig named default is read directly by name and does not need this label. For example:

    apiVersion: apiextensions.crossplane.io/v1beta1
kind: EnvironmentConfig
metadata:
  name: team-storage
  labels:
    storages.pkg.internal/name: team-storage
data:
  storage:
    providerConfigName: team-minio

    Select this config on a Storage with:

    spec:
  environmentName: team-storage

    Apply the updated Storage XRD before setting spec.environmentName. Use a lowercase DNS name with 1 through 63 characters. Config names used in labels must also be valid label values. EnvironmentConfigs are cluster-scoped, so Storages with the same name use the same config for the final layer across namespaces.

    storage.providerConfigName selects an existing backend ProviderConfig. When unset or blank, AWS, MinIO, OTC, and OVHcloud use provider-aws, provider-minio, provider-otc, and provider-ovh. CloudFerro requires an explicit provider name. Its project manifests use spec.environmentName: storage-cloudferro-<project-id>.

    Resource scope and credentials

    Consumer Secrets are native composed resources. A namespaced Storage can compose these Secrets even when its cloud provider has only cluster-scoped resources. Those cloud resources still need Object adapters. Crossplane cannot compose a cluster-scoped resource directly from a namespaced Storage. See Crossplane resource scope.

    The provider-kubernetes runtime redacts Secret data from Object status. Keep the MinIO runtime's logging configuration to prevent credentials from appearing in provider logs.

    For cleanup scheduling and Job limits, see Lifecycle rules.

    Replace a Storage

    A new Storage can adopt existing composed resources after the old Storage releases them. Before replacing a Storage, prevent its source manifests from creating it again. Delete the old Storage with Kubernetes orphan propagation (--cascade=orphan) to keep its composed resources. Wait until the old Storage is gone and its controller references are removed.

    Create the replacement in the same namespace. Keep the backend, provider configuration, project, region, principal, provider identity, and bucket names the same. The Composition can then adopt resources with the same kind and name. Preserve their external-name annotations and provider ownership markers. Consumer Secrets and credentials can be recreated if needed.

    Do not use a failed deletion of a non-empty bucket as a handover method. Its managed resource can remain in deletion, which prevents reuse. The pinned MinIO provider also rejects an existing bucket when a new Bucket resource lacks its ownership marker. Keep the existing Bucket resource and its Object adapter. Recreating managed resources from cloud resources requires provider-specific import.

    2. Install the configuration package

    Install one Configuration package for each backend you need. Each package contains its backend Composition and depends on ghcr.io/versioneer-tech/provider-storage/api from the same release. Crossplane installs that API package once. It owns the shared Storage XRD. Only the selected backend Compositions are installed. Provider controllers, functions, and credentials are installed separately in step 1. Use the same release for all installed backend packages.

    Keep dependency resolution enabled on the Configuration resources; this is the default. Do not set spec.skipDependencyResolution: true.

    For later upgrades of this package layout, update the existing API Configuration to the target release, then update all backend Configurations. Crossplane does not upgrade installed dependencies automatically by default.

    Older backend packages own the XRD directly. Moving that ownership to the API package needs a separate migration before upgrade. Do not delete the XRD or its CRD: this can delete existing Storage resources. The ownership migration is not provided here.

    After the backend dependencies are ready, create a Configuration manifest. Use the name and package for your backend:

    Backend Name Package
    MinIO storage-minio ghcr.io/versioneer-tech/provider-storage/minio:0.5.0
    AWS storage-aws ghcr.io/versioneer-tech/provider-storage/aws:0.5.0
    OTC storage-otc ghcr.io/versioneer-tech/provider-storage/otc:0.5.0
    OVHcloud storage-ovh ghcr.io/versioneer-tech/provider-storage/ovh:0.5.0
    CloudFerro storage-cloudferro ghcr.io/versioneer-tech/provider-storage/cloudferro:0.5.0

    Use the selected values in this manifest:

    apiVersion: pkg.crossplane.io/v1
kind: Configuration
metadata:
  name: <configuration-name>
spec:
  package: <package>

    Replace the placeholders with values from the table and your package version. Save the manifest as configuration.yaml, then apply it:

    kubectl apply -f configuration.yaml

    Check that the configuration, providers, and functions are healthy:

    kubectl get configurations,providers,functions

    If the cluster has more than one Provider Storage Composition, each Storage resource must select its backend explicitly. A selector is not needed when only one compatible Composition is installed. See Select a backend.

    3. Verify the installation

    Use the bucket example in the target namespace. Set its selector to your installed backend. Check that the Storage becomes ready and that its consumer credentials permit the expected S3 operations. See Use Storage for backend selection, credential rollover, lifecycle rules, and verification commands.

    For cloud backends, keep the project, endpoint, and region in the EnvironmentConfig consistent with the settings saved by bootstrap-iam.sh.
